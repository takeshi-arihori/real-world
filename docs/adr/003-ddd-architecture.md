# ADR-003: DDD・クリーンアーキテクチャの採用

## ステータス

承認済み

## コンテキスト

プロジェクトが成長するにつれ、以下の課題が顕在化することが予想される。

- **ドメインの複雑性**: ビジネスルールが増加するにつれ、従来の MVC 構成ではロジックが Controller や Model に散在し、変更影響範囲の把握が困難になる
- **保守性**: Service クラスが肥大化し、単一責務の原則が崩れやすい。レイヤー間の依存が明確でないため、変更時の副作用が予測しにくい
- **テスタビリティ**: ビジネスロジックがフレームワーク（Eloquent 等）に密結合していると、単体テストが書きにくく、テスト実行速度も低下する
- **チーム開発**: 複数人で開発する際に、コードの配置基準が曖昧だと一貫性が保てない

## 決定

DDD（ドメイン駆動設計）ベースの4層アーキテクチャを採用する。

- **Domain 層**: ビジネスルール・ドメインロジック（Entity, ValueObject, Repository Interface, Domain Service, Domain Event）
- **Application 層**: ユースケースの実行・調整（Command, Query, DTO）
- **Infrastructure 層**: 永続化・外部サービス連携（Eloquent Model, Repository 実装, 外部 API クライアント）
- **Presentation 層**: HTTP リクエスト/レスポンス（Controller, FormRequest, JsonResource）

依存方向は外側から内側へのみ許可し、Domain 層は他のどの層にも依存しない。

併せて、読み取り系と書き込み系をクラスレベルで分離する CQRS-lite パターンも導入する。

## 理由

### 代替案との比較

| アーキテクチャ | メリット | デメリット | 採否 |
|--------------|---------|-----------|------|
| **従来の MVC** | シンプル、学習コスト低い | ロジック散在、Model 肥大化、テスト困難 | 不採用 |
| **DDD 4層（採用案）** | 関心の分離が明確、テスタビリティ高い、ドメイン知識がコードに反映される | ファイル数増加、学習コスト | 採用 |
| **Hexagonal Architecture** | ポート＆アダプタで柔軟 | 4層との差異が小さく、Laravel との親和性は4層の方が高い | 不採用 |
| **CQRS（完全分離）** | 読み書き完全分離で最適化可能 | 複雑性が高い、イベントソーシングが前提になりがち | 不採用（lite版を採用） |

### 採用理由

1. **Domain 層の独立性**: フレームワークに依存しないため、Laravel のバージョンアップやフレームワーク変更時の影響を最小化できる
2. **テスタビリティ**: Domain 層は純粋な PHP クラスで構成されるため、高速な単体テストが可能
3. **明確な配置基準**: 4層の責務が明確なため、新しいコードの配置先で迷いにくい
4. **段階的導入**: 既存の Laravel 構成から段階的に移行でき、全面的な書き換えは不要

## 影響

### ポジティブな影響

- ビジネスロジックの可読性・保守性が向上する
- テストカバレッジを高めやすくなる
- コードレビュー時の判断基準が明確になる

### トレードオフ

- **学習コスト**: DDD の概念（Entity, ValueObject, Repository パターン等）の理解が必要
- **ファイル数の増加**: 1機能あたりのファイル数が増える（Entity, Repository Interface, Repository 実装, UseCase, DTO 等）
- **初期開発速度**: 単純な CRUD でもレイヤーを意識する必要があるため、初期の開発速度は MVC より遅くなる可能性がある
- **Entity と Eloquent Model の変換コスト**: Repository 実装内で変換処理が必要になる

### リスク軽減策

- `docs/rules/backend.md` に判断基準フローチャートとアンチパターン一覧を整備し、迷わないようにする
- 単純な CRUD の Query（読み取り）では Eloquent 直接利用を許容する（CQRS-lite）
- 新規機能から段階的に適用し、既存コードは必要に応じてリファクタリングする

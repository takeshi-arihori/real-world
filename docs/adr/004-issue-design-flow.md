# ADR-004: Issue読み込み→要件設計→タスク分解フローの導入

## ステータス

承認済み

## コンテキスト

Issue 起点で TDD 開発を行う際、「Issue を読む → 即実装」になりがちで以下の問題があった：

- 設計判断が暗黙知になる
- タスクの粒度がバラつく
- レビュー時に「なぜこの設計か」が追えない

## 決定

Issue → 要件整理 → 設計ドキュメント → タスク分解 → TDD 実装の一貫したフローを構築する。

具体的には：

1. `docs/design/_template-feature-spec.md` をテンプレートとして用意
2. Issue 着手時に `specs/<feature>.md` として設計ドキュメントを作成する（`specs/` は gitignored）
3. `tdd-issue` スキルに設計ステップを組み込み、設計なしに実装に入れないガードを設ける
4. Issue ラベル (`needs-design`, `ready`, `frontend`, `backend`, `fullstack`) で進行状況を可視化

## 理由

- **テンプレート化**により設計の抜け漏れを防止できる
- **設計ドキュメント**がレビュー時の判断根拠になる
- **スキルへの組み込み**により、フローのスキップを防止できる
- **ラベル運用**により、Issue の状態が一目で分かる

代替案として「口頭で設計を共有する」方法もあるが、記録が残らず再現性がないため不採用。

## 影響

- Issue 着手から実装開始までのリードタイムが若干増える
- 設計ドキュメントのメンテナンスコストが発生する
- 一方で、レビュー効率とコード品質の向上が期待できる
